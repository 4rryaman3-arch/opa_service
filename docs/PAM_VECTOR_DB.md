# PAM model and configuration knowledge database

`vector.db` is a portable SQLite knowledge database generated by the running
PAM Django application. It is an input to OPM test generation; it is not OPM's
operational `opm.db` or `regintel/catalog.db`, and OPM never writes to it.

## Generate it in PAM

Run this from the deployed Django application directory so the complete merged
platform and PAM app registry has loaded:

```console
python manage.py getpamcapablities --output vector.db
```

The command exports:

- every installed Django model and field's schema metadata;
- public, safely serializable values from
  `configuration.configuration_constants` after product constant extension;
- collected and lookup PAM evidence capabilities, modes, fields, source models,
  caveats and field meanings; and
- the configuration setting source map used by OPM.

It does **not** export model rows, Django settings, secrets, tokens, passwords,
connection strings, or Python callable implementations. Existing files are not
replaced unless `--force` is supplied. `--app` and `--constant-module` may be
repeated to restrict or extend the export.

## Interpret it and generate tests in OPM

```console
python scripts/generate_pam_vector_tests.py \
  --db vector.db \
  --output pam-vector-tests.json \
  --validate
```

OPM opens the database with SQLite `mode=ro&immutable=1`, checks the schema,
SQLite integrity, and every document digest, then:

1. checks every advertised evidence type, version, and field against OPM's
   pinned evidence schemas;
2. resolves each capability's source-model labels against exported Django
   metadata, with explicit `EXACT`, `OBJECT_NAME`, `AMBIGUOUS`, or `MISSING`
   resolution;
3. produces a valid representative record for each capability;
4. produces rejection cases for unknown fields and missing required fields; and
5. validates all generated cases when `--validate` is used.

These schema vectors complement the rule-specific PASS/FAIL/boundary cases
already generated by `regintel.generated_rules.build_cases`. A
`LOOKUP_AVAILABLE` capability remains testable but is not treated as a live
collector until PAM advertises it as `COLLECTED`.

The interpreter is also available as a Python API:

```python
from regintel.pam_vector_db import PamVectorDatabase, generate_test_vectors

with PamVectorDatabase("vector.db") as database:
    password_policy = database.capability_context("password_policy_configuration")
    matching_documents = database.search("session recording")
    vectors = generate_test_vectors(database)
```

## Use by live rule generation

The catalog worker reads the database named by `OPM_REGINTEL_VECTOR_DB` (`scripts/run_native.py` sets it to
`data/vector.db` when that file exists). For each generation job:

1. the database is validated and its schema tests run first; a missing, invalid or failing database stops generation
   with `PAM_VECTOR_DB_INVALID`;
2. a generated rule is activated only if every field it uses is listed as collected (otherwise `COLLECTOR_MISSING`);
3. rules get `pam_stored_null_*` cases for unused fields whose same-named source-model field may be empty; and
4. the job result records the database digest. A new digest makes the model propose again for uncovered requirements.

Nothing from `vector.db` is added to a model prompt. Vetted (non-generated) rules are not affected.
